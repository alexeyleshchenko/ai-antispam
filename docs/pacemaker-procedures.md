# ai-antispam — Pacemaker cron procedures

**Owns:** the procedure behind every `ai-antispam-*` pacemaker cron. The crons are THIN WAKES (P7 — cron is a pacemaker, not the worker): each one wakes its owning lane and stops. Everything substantive lives HERE, never in a cron prompt — a cron prompt cannot be updated by a skill change, so work left in one goes stale silently.

**The notify leg — the prompt shape (board #118, fixed 2026-10-16).** Every pacemaker delivers its wake with the prompt's own `session notify`. Until 2026-10-16 that command was BACKGROUNDED — `nohup … > /tmp/<job>-<ts>.log 2>&1 &` — and the prompt then hard-coded `Report "Dispatched."`. That makes the trigger's exit status the **LAUNCH's**, so a wake that dies on the wire still records `Dispatched.`: twice, 2026-10-14 and 2026-10-15, the first costing the Bot lane **18.8 h idle**. The shape is now FOREGROUND, status propagated, report CONDITIONAL:

```bash
timeout 110 /usr/local/bin/opencrabs -p ops session notify <target> --text "<wake text>" --title "<job> $(date -u +%Y-%m-%dT%H)" --mode quiet --quiet-for-secs 20 --max-delay-secs 30; rc=$?; echo "notify_exit=$rc"
```

- **No `nohup`, no trailing `&`.** `timeout 110` replaces the backgrounding — it holds the command inside the tool budget while still propagating the notify's OWN status.
- **The wall is 110 s, and the ceiling is the bash tool's 120 s default** (board #120, 2026-10-17). It was 60 s, and that killed **11 wakes in two days** with `exit 124` (6 on 10-16, 5 on 10-17; enumerated from `cron_job_runs`, predicate `content LIKE '%notify FAILED (exit 124)%'` — the item body's original count of 9 was read mid-day and both figures have since moved) — the wall was measuring the wrong thing. The notify POST itself answers in **0.82 s**; what costs the time is that every `opencrabs` start pays an O(n) read+parse of `tmp/detached` (**27,343** files / 110 MB pre-prune, opened **twice** — `mark_orphans_interrupted` then `cleanup_stale`) before it does anything. Full-command wall measured **66.36 s / 47.64 s / 43.00 s** (cold page cache), and a live run under the new wall took **46.33 s** with `notify_exit=0`. Root cause is fork **#783** with a provable stat-first fix; this wall is the interim. **Do not raise it past 120 s**: above the bash tool's default the foreground command is handed to the background manager, the `rc` is lost, and the #118 silent-success defect comes straight back.
- **The startup cost is cache-dependent, so measure it in both regimes.** Same directory, same binary: **cold** page cache → `cron list` 34.29 s / 79.10 s and read+parse 40.09 s; **warm** → 6.97 s / 4.34 s. A wake that lands after an idle period is the cold case, which is exactly when the wall bites. A single warm measurement is not evidence that the cost is gone.
- **The interim prune (2026-10-17, board #120) was SUPERSEDED the next morning by a host wipe — do not re-derive its conclusions.** 14,011 terminal status files older than 2 days were moved (not deleted) to `tmp/detached-pruned-20261017T0715Z/`, taking `detached/` from 27,426 to ~13.4k files and cold `cron list` from 34.29 s to **26.63 s**; the move was verified free of `Running`/`Pending`/`AwaitingInput` beforehand, so zero live files were touched. **On 2026-10-18T03:00-03:02Z the host emptied both directories and deleted the bucket**: `/usr/local/bin/vds-cleanup.sh:54` (md5 `45e5efa2214adfc4e2d8e6613e16e355`, system cron **weekly — Sunday 03:00**, `0 3 * * 0`: the day-of-week field alone restricts it, day-of-month is `*`; the script's own header prints `=== Weekly cleanup at ...` and its log holds 5 runs, every one a Sunday — Sep 20 · 27 · Oct 4 · 11 · 18, each `03:00:01Z`) runs `rm -rf /root/.opencrabs/tmp/* /root/.opencrabs/profiles/ops/tmp/*`, guarded on `! command -v docker` — true on this host. Measured result at 06:19Z: `runs/` 56,544 → **1,708** files / 4.5 MB, `detached` 14,243 → **860** / 3.5 MB, bucket **gone**, `tmp` 272 MB → **8.0 MB**, cold `cron list` **1.28 s**. Both dirs now begin at the wipe instant (`runs` 03:02:38Z, `detached` 03:02:34Z). There is therefore no restore command to run and **no 2026-10-22 date to cite** — that watch date is moot.
- **The sweeps' blind spots are real, but the host `rm` has none.** `cleanup_stale` (`src/brain/agent/service/work_status.rs:837`) iterates `fs::read_dir(&dir)` — top level only — and its own comment records the rule: *"Streams live in `runs_dir()`, a SIBLING of the status dir, so the loop above never sees them."* A sibling bucket is immortal **to OpenCrabs' sweeps** (57 MB that only a human `rm -rf` could reclaim) — and `cleanup_old_temp_files`'s doc block adds that *"Subdirectories are never recursed into"*, so a nested bucket is invisible to both. **The host script is not bound by either rule, which is why the bucket died.** `runs/` is still NOT a leak and must not be read as one: it has its own sweep (`sweep_stale_runs`, `work_status.rs:895`, reached from `logging::cleanup_old_temp_files`, which `main.rs` runs on every surface — the runs leg lives there *because `cleanup_stale` is called from the TUI alone*). **Report the breakdown, never a bare `tmp` total**: a total conflates a swept leg, a host-wiped leg and (formerly) an immortal one.
- **Bound: the population is capped at ONE WEEK of creation — the host wipe is WEEKLY, not daily.** `crontab -l` carries `0 3 * * 0 /usr/local/bin/vds-cleanup.sh` (day-of-week 0 = Sunday, day-of-month `*`, so the dow field alone restricts it), the script's own header prints `=== Weekly cleanup at ...`, and its log holds **5 runs, every one a Sunday** (Sep 20 · 27 · Oct 4 · 11 · 18, each `03:00:01Z`). The peak therefore lands immediately **before** each wipe, not after it, and the bound is **7 × rate**. At 1.465 ms/file (40.09 s ÷ 27,357, measured 2026-10-17 pre-wipe — a one-point through-origin fit, corroborated independently at 860 files: 1.26 s predicted vs 1.28 s measured; the two `cron list` wall times miss it by +6.97 s and −5.90 s in opposite directions, i.e. load noise, so a projection carries ±8 %): **3,679/day** (07:15→12:05Z on 10-17) → 25,753 files → **37.7 s**, **2.91×** headroom; **6,548/day** (03:02→06:19Z on 10-18, a 3.3 h window) → 45,836 → **67.2 s**, **1.64×**; **8,070/day** (the 10-16 window) → 56,490 → **82.8 s**, **1.33×**. Breach needs **≈10,723/day sustained** (110 s ÷ 1.465 ms = 75,063 files over 7 days), which no observed window approaches. **The rate is workload-dependent — state the window or state no rate.** The 7-day sweep is a genuine co-bound, but its period is **per process start, not per day** — `cleanup_stale` is reached from `recover()` (`restart_recovery.rs:546` → `reconcile.rs:39`, `STALE_AFTER` = 7 d), which runs on every surface including the headless daemon (ops log: `Recovered 4 item(s) interrupted by restart`, 2026-10-18T07:03:22Z), so a daemon that never restarts bounds at 7 days **plus uptime**. The wipe's extra effect is that it removes the peak rather than trimming it. **A null deletion result on 2026-10-22 is therefore EXPECTED, not a failure** — the weekly wipe removes everything at exactly 7 days, so nothing ever reaches the sweep's cutoff, and a null result is not evidence about #783. The real failure mode to watch is therefore the host wipe disappearing: it is the load-bearing clock, because the sweep's period is per process start, not per day. **Worst case to sample: 2026-10-25 02:5xZ, immediately before the next wipe.**
- **A wall proof is scoped to what it measured.** The 2026-10-17 probe (run `a44c525c`, **89.2 s**, `Dispatched.`) proves the wall covers **startup at the current population**, because its ~89 s is startup-dominated (~2 × 40 s parse passes). It does **not** prove coverage of a *parked or busy* lane, whose delay is a different term entirely. Do not cite it as that proof.
- **Report conditionally, never unconditionally:** `notify_exit=0` → `Dispatched.`; any non-zero → `❌ notify FAILED (exit <value>) — the wake did not land. Do not retry.` A hard-coded `Dispatched.` is a NAME, not a predicate.
- **`--mode quiet` still requires `--max-delay-secs 30`** (the default starvation cap is 1800 s and would block past the budget), and the unique `--title` still stops the bash retry guard latching permanently.
- **One wake proves neither class.** `session notify` exits 0 on the delivered/deferred path and non-zero on a dead target (`no_route`, exit 2), so the leg is proven by a PAIR: a bogus target (controlled failure → the run row reads the FAILED line) and a valid one (positive control → the run row reads `Dispatched.`). Measured 2026-10-16: run `64b2d7ea` (bogus) → `❌ notify FAILED (exit 2)`; run `d6edf42f` (valid) → `Dispatched.`
- **The run record's predicate is `content`, never `status`.** Both probe runs above carry `status='success'` in `cron_job_runs`: `status` describes the TURN, and a turn that correctly reports a failed wake is a successful turn. The outcome lands in `content` — key a watcher on that column, never on `status`, or it stays blind to exactly this class. (Surfaced by Triage 2026-10-16.)
- **Do NOT delete a probe job to tidy up.** `cron_job_runs.job_id` is declared `ON DELETE CASCADE`, so removing the job can take its run rows — the very evidence — with it. Disable it instead.
